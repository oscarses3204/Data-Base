l

Projection can be implemented by removing unwanted attributes
from each tuple as query result tuples are produced.

☞ May result in duplicate tuples unless a candidate key
is in the projection.

l

The query result tuples will be smaller in size than the original
tuples.

☞ The size reduction depends on the

number and size of eliminated attributes.

☞ Fewer write page I/Os are required
to produce the query result.

l

There is no additional cost for projection unless duplicate tuples
need to be eliminated (i.e., select distinct …).

l

For duplicate elimination we can use modified external sorting.
Modify sort pass to eliminate unwanted attributes (e.g., sailorId, rDate).
Ø

Thus, sorted runs contain smaller tuples.
(Size reduction depends on the number and size of eliminated attributes.)

Modify merge passes to eliminate duplicates.
Ø

Thus, there are fewer output tuples than input tuples (i.e., tuples read).
(The difference depends on the number of duplicates.)

Cost: Sort pass: read in the original relation and write out the same number of
smaller tuples ⟹ there are fewer write than read page I/Os
since more (smaller) tuples can be placed on a page.

Merge passes: read in smaller tuples and write out fewer tuples in each
pass ⟹ there are fewer write than read page I/Os since
there are fewer tuples after duplicates are eliminated.

HASH-JOIN
l

A hash function h is used to place tuples
of both relations into n partitions (buckets)
(i.e., a hash file organization).

☞ This partitions the tuples of each of

the relations into sets that have the
same hash value on the join attributes.

l

l

Only need to compare r tuples in
partition ri with s tuples in partition si.
Do not need to compare r tuples in partition
ri with s tuples in any other partition, since:

– An r and an s tuple that satisfy the join condition
have the same value for the join attribute.

Cost: 3 * (Br + Bs)

⟹ 1 read and 1 write to
create the partitions;

1 read to compute the join.

– Hence, both hash to the same partition (hash value) in r and s, respectively.
⟹ Each tuple must be in, respectively, partition i in r and partition i in s!

☞ Can be used only for equi-joins and natural joins.

HASH-JOIN ALGORITHM
/* Create partitions */
1. Partition the relation r using the hash function h.
– h maps JoinAttributes values to {0, 1, ..., n-1} (i.e., n partitions), where
JoinAttributes denotes the common attributes of the natural join of r and s.
– r0, r1, …, rn-1 denote n partitions (buckets) of r tuples.
Ø Each tuple tr Î r is in partition ri, where i = h(tr [JoinAttributes]).

– s0, s1, …, sn-1 denote n partitions (buckets) of s tuples.

Ø Each tuple ts Î s is in partition si, where i = h(ts [JoinAttributes]).

– One page of the buffer is reserved as the output page for each partition.
2.

Partition s similarly.
☞ Need to read and write r and s to create the partitions.

/* Perform indexed nested-loop join using hash index */
3. For each i:

– Load partition ri into the buffer and build an in-memory hash index on it
using the join attribute. This hash index uses a different hash function than
the earlier one h. Relation r is called the build input.

– Read the tuples in partition si from the secondary storage page-by-page.
For each tuple ts locate each matching tuple tr in ri using the in-memory
hash index. Relation s is called the probe input.

COMPLEX JOINS
l

Join with a conjunctive condition: r JOINq1Ùq2Ù…Ùqn s
1. Use either nested-loop/block nested-loop join, or
2. Compute the result of one of the simpler joins r JOINqi s
Ø This join result contains those tuples that also satisfy the remaining
conditions q1Ù…Ùqi –1Ùqi +1Ù…Ùqn.
Ø Check the remaining conditions in the buffer.

l

Join with a disjunctive condition: r JOIN q1Úq2Ú…Úqn s
1. Use either nested-loop/block nested-loop join, or
2. Compute the result as the union of the records in the individual
joins
(r JOINq1 s) È (r JOINq2 s) È … È (r JOINqn s)

☞ Useful only if all conditions are restrictive (selective).

EVALUATION USING PIPELINING (cont’d)
l

Algorithms that cannot output tuples as they get input tuples are
called blocking.

☞ Merge join and hash join are blocking since they require operation
results to be written to secondary storage and then read back.

l

There are variants of these algorithms that generate (at least
some) results on-the-fly as input tuples are read.

☞ Hybrid hash join generates output tuples even as probe relation
tuples in the in-memory partition (partition 0) are read.

Pipelined Join: Hybrid hash join can be modified to buffer tuples in the
first partition (partition 0) of both relations in-memory, reading them as
they become available, and outputting matching result tuples between
the tuples in the first partition.
Ø When a new r0 tuple is found, match it with existing s0 tuples, output
matches, and save it in r0.
Ø This can also be done symmetrically for s0 tuples.
