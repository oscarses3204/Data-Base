LOCKING
Lock: a mechanism to control concurrent access to a data item.
l

A data item Q can be locked in one of two modes:
1. shared-mode (shared lock)

Ø Can only read Q; transaction requests with a lock-s(Q) instruction.

2. exclusive-mode (exclusive lock)

Ø Can both read and write Q; transaction requests with a lock-x(Q) instruction.

Ø A data item Q is unlocked with an unlock(Q) instruction.
l

A transaction must make a lock request to the concurrency-control
manager before accessing a data item.
– A transaction can proceed only after a request is granted.

– A transaction should not request a lock until it is needed.

☞ The concurrency control manager should allow only
conflict-serializable schedules that are recoverable.

TWO-PHASE LOCKING (2PL) PROTOCOL
Phase 1: Growing Phase (request or upgrade locks)

– Acquire a lock-s or lock-x or upgrade a lock-s to a lock-x on a data item.

Phase 2: Shrinking Phase (release or downgrade locks)

– Release a lock-s or lock-x or downgrade a lock-x to a lock-s on a data item.

Using 2PL, transactions can be serialized in the order of their lock
points (i.e., the point where a transaction acquired its final lock).

☞ If a schedule is executed by 2PL, then
it must be conflict serializable.

☞ If a schedule is conflict serializable, then
it may or may not be executed by 2PL.

☞ Not all conflict serializable schedules are allowed by 2PL.
Revised Locking Etiquette

To maximize concurrency, a transaction normally should request only a lock-s before
reading a data item and upgrade it to a lock-x only when it wants to write the data item.

STRICT AND RIGOROUS TWO-PHASE LOCKING
Strict Two-phase Locking
– Requires that all exclusive-mode locks be held until after a transaction
commits (shared-mode locks can be released anytime).

Rigorous Two-phase Locking
– Requires that all locks (both shared-mode and exclusive-mode) be held
until after a transaction commits.
l

l

Both protocols ensure that any data written by an uncommitted
transaction are locked in exclusive mode until the transaction commits
and so cannot be read by another transaction.
The transactions can be serialized in the order in which they commit.

☞ Strict and rigorous 2PL schedules are
recoverable and cascadeless.

DEADLOCK PREVENTION
Order lock requests

Impose a partial/total ordering of all data items and require transactions to
lock data items only in the order specified by the partial/total order.

Pre-emptively rollback transactions before deadlock happens
A transaction waits for a lock only for a specified amount of time after
which it is rolled back.
Wait-die Scheme

Ø An older transaction waits for a younger one to release a data item; a
younger transaction never waits for an older one to release a data item but is
rolled back (dies) instead.

Wound-wait Scheme

Ø A younger transaction waits for an older one to release a data item; an older
transaction wounds (forces the rollback of) a younger transaction instead of
waiting for it.

Starvation is possible; can be handled using timestamps as "age".

The lock table is usually implemented as an in-memory hash
table indexed on the name of the data item being locked.

18.5.1

TIMESTAMPS
Each transaction is issued a fixed timestamp TS(Ti)
by the system before it starts execution.
If the most recent transaction Ti has timestamp TS(Ti), a new transaction Tj
is assigned timestamp TS(Tj) such that TS(Tj) > TS(Ti).

☞ The timestamps determine the serializability order.

☞ If TS(Ti) < TS(Tj), then Ti must not be allowed to see any results of Tj
since Tj started later in time than Ti.

l

To implement serializability, two timestamp values are associated with
each data item Q.

RTS(Q) (read timestamp) the largest timestamp of any transaction that
executed read(Q) successfully.

WTS(Q) (write timestamp) the largest timestamp of any transaction that
executed write(Q) successfully.

The timestamps of Q are updated whenever a new read(Q) or write(Q)
instruction is executed.

RECOVERABILITY AND CASCADING ROLLBACK
l

The problem with the timestamp-ordering protocol:
– Suppose Ti aborts, but Tj has read a data item written by Ti.
– Then Tj must abort; if Tj had been allowed to commit before Ti
aborted, the schedule is not recoverable.
– Moreover, any transaction that has read a data item written by Tj
must abort.

☞ This can lead to cascading rollback.
Solution
– A transaction is structured such that all its writes are performed at the
end of its processing.
– All writes of a transaction form an atomic action; no transaction may
execute while a transaction is being written.
– A transaction that aborts is restarted with a new timestamp.

l

Multiversion schemes keep old versions of data items, labelled
with timestamps, to increase concurrency.
– Multiversion Two-Phase Locking (2PL)
– Multiversion Timestamp Ordering

l

Each data item Q has a sequence of versions <Q1, Q2, …, Qm>.

l

Each version Qk contains three data fields:

Content The value of version Qk.
WTS(Qk) The timestamp of the transaction that created (wrote)
version Qk.
RTS(Qk) The largest timestamp of a transaction that successfully
read version Qk.

l

Each successful write by a transaction Ti creates a new version
Qk of Q and sets Qk’s RTS and WTS to TS(Ti).
