DATABASE BUFFER
Data must be in main memory for an application to operate on it!
l

l

To reduce retrieval time, DBMSs try to minimize page transfers
between main memory and secondary storage.
The number of accesses to secondary storage can be reduced
by keeping as many pages as possible in main memory.

Buffer – the portion of main memory available to store copies of

☞ NOTE: main memory space for storing pages is limited!
Buffer manager – the operating system (OS) subsystem that
manages the main memory buffer space.

☞ The goal of the buffer manager is to

minimize accesses to secondary storage.

BUFFER MANAGER
l

l

l

An applications makes a read request to the operating system buffer
manager when a page is needed from secondary storage.
If the page is already in the buffer, the requesting application is given
the page's address in main memory and accesses it directly.
If the page is not in the buffer:

– The buffer manager allocates space in the buffer for the page, replacing
some other page, if necessary, to make space for the new page.

– The page that is replaced is written back to secondary storage only if it was
modified since the most recent time that it was written to/read from
secondary storage.
– Once space is allocated in the buffer, the buffer manager reads the page
from secondary storage into the buffer and passes the page's address in
main memory to the requesting application.

l

We refer to each page read as an input page access and each page
write as an output page access (or page I/O).

BUFFER PAGE REPLACEMENT POLICIES
l

l

Most operating systems replace the page
least recently used (LRU strategy).

Suppose the buffer can
hold 10 pages and
relation s needs 8 pages.

LRU can be a bad strategy for certain access
patterns involving repeated scans of data.
Example: compute the join of two relations
r and s using a nested loop.
Best in this case: replace the page most recently
used (MRU strategy).

l

A DBMS usually has its own buffer manager
that uses statistical information regarding the
probability that a request will reference a
particular page to retrieve and replace pages.

EXAMPLE HASH FILE ORGANIZATION (cont’d)
l

This organization can efficiently answer queries of the form:
Find all employees whose salary is equal to X.

l

l

l

To answer this query, we compute the hash value of X and then search
only in the corresponding page computed by the hash function.
A page may contain records of employees with different salaries that
produce the same hash value (e.g., employees with salary 20,500 also
hash to page 254). This is not a problem because, since we retrieve
the page into the buffer, we can check all its records in main memory
and select only the ones that satisfy the query condition.
If there are no overflow pages, answering the query requires that just
one page be read (i.e., one page I/O).

☞ If there are overflow pages, we must retrieve all of them. Why?
l

Hashing is not good for range search (e.g., Find all employees with
salaries between 15,000 and 16,000) because the records of these
employees may be stored in many different pages.

DATA DISTRIBUTION: REPLICATION
l

Problems with consistent hashing:

– If two servers are mapped too close to one another,
one of these ends up with few keys to store.
– When a server is added, all the keys moved to this
new server originate from just one other server.
l

Instead of mapping a server S to a single point on the ring, it is
mapped to multiple positions, called (logical) replicas.
– For each physical server S, we end up with r points (the number of
replicas) on the ring, called virtual nodes.

Note: Each replica (virtual node) still represents the same physical instance.

replicate key-value pairs across multiple servers.

– E.g., we can store a key-value pair on two or more servers clockwise
from the key’s position on the ring.
