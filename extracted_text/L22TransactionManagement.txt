17.1

OVERVIEW
A transaction is a unit of program execution that
accesses, and possibly updates, the database.
l

A transaction must preserve database consistency.
– During transaction execution the database may be inconsistent.
– However, when the transaction commits (ends), the database must
be consistent.

l

Two main issues to deal with:
– Concurrent execution of multiple transactions.
Ø Handled by concurrency control.

– Failures of various kinds (e.g., hardware, system crashes, etc.).
Ø Handled by database recovery.

ACID PROPERTIES
Atomicity

Either all instructions of a transaction are properly reflected in the
database, or none are.

Consistency

Execution of a transaction in isolation (i.e., it is the only transaction
executing) preserves the consistency of the database.

Isolation

Concurrently executing transactions must be unaware of other
concurrently executing transactions. Intermediate results of a transaction
must be hidden from other concurrently executing transactions.
Ø For every pair of transactions Ti and Tj, it appears to Ti that either Tj finished
execution before Ti started or that Tj started execution after Ti finished
(i.e., either Ti executes before Tj or Tj executes before Ti ⟹ serial execution).

Durability

After a transaction completes successfully, the changes it made to the
database persist, even if there are system failures.

17.5

CONCURRENT EXECUTIONS AND ISOLATION
l

Advantages of concurrent transaction execution:
– increased system utilization, leading to better transaction throughput
since one transaction can be using the CPU while another is reading
from or writing to secondary storage.
– reduced average response time for transactions. Short duration
transactions do not need to wait behind long duration ones.

☞ Concurrent execution, if not handled properly, can lead to
violation of the isolation property.

(A transaction can see the partial, incomplete results of another transaction).
l

Concurrency control schemes are mechanisms used to
achieve isolation in the presence of concurrent executions.

☞ They control the interaction among the concurrent transactions to
prevent them from destroying the database consistency due to
problems that can arise when concurrent transactions access the
same data.

17.5

SCHEDULES
l

A schedule is a sequence of instructions showing the chronological
order in which instructions of concurrent transactions are executed.
– A schedule for a set of transactions must consist of all instructions of
those transactions.
– A schedule must preserve the order in which the instructions appear in
each individual transaction.

l

To preserve database consistency, a schedule for executing
transactions must be one of the following.
serial

Transactions are executed one at a time, one after another.
⟹ All the instructions of a transaction are executed
before the next transaction starts executing.

serializable Transactions are executed concurrently (i.e., at the same
time, all together) in an interleaved manner so that their
execution is equivalent to a serial schedule.

SERIALIZABILITY
Basic Assumption
Each transaction preserves database consistency.

☞ A serial execution of a set of transactions
always preserves database consistency.

l

l

A (possibly concurrent) schedule is serializable if it is equivalent
to a serial schedule.
We ignore instructions other than read and write instructions
and assume that transactions may perform arbitrary
computations on data in the buffer in between reads and writes.

☞ Our simplified schedules consist of only
read and write instructions.

CONFLICT SERIALIZABILITY
Instruction li of transaction Ti and instruction lj of transaction Tj
conflict if and only if there exists some data item Q accessed by
both li and lj and at least one of these instructions is write( Q).
1. li = read(Q), lj = read(Q).
2. li = read(Q), lj = write(Q).
3. li = write(Q), lj = read(Q).
4. li = write(Q), lj = write(Q).
l

l

li and lj do not conflict.
li and lj conflict.
li and lj conflict.
li and lj conflict.

Intuitively, a conflict between two instructions li and lj of two
different transactions Ti and Tj forces a (logical) temporal order
between them.
If li and lj are consecutive in a schedule and they do not conflict,
the result of their execution would remain the same even if they
had been interchanged in the schedule.

RECOVERABILITY
A schedule is recoverable if a transaction Tj that reads a data item
previously written by another transaction Ti commits after Ti.
☞ If Ti aborts, then Tj should not have read the data item written by Ti. Thus, Tj should
also be aborted. However, if Tj has already committed, then it cannot be aborted.

☞ A schedule that is not recoverable
violates the durability property.

T2 reads a data item, A, written by T1.

T2 commits immediately after the read.

If T1 aborts, which will undo the write of A,
then T2 should also abort since it read
data item A written by T1.

CASCADELESS SCHEDULES
A schedule is cascadeless if, for each pair of transactions Ti and
Tj where Tj reads a data item previously written by Ti, the
commit instruction of Ti appears before the read instruction of Tj.

☞ Tj does not read a data item written by Ti until after Ti commits.

l

Cascadeless schedules are schedules where cascading
rollbacks cannot occur.

☞ Every cascadeless schedule is also recoverable.
l

It is highly desirable to restrict the schedules to those that are
cascadeless to avoid rollbacks of other transactions when a
transaction aborts.

IMPLEMENTATION OF ISOLATION
l

Schedules must be serializable, and recoverable, to ensure
database consistency, and preferably, cascadeless.

– A policy whereby only one transaction can execute at a time generates
serial schedules but provides no concurrency.

☞ Testing a schedule for serializability
after it has executed is too late!

Goal: Develop protocols that both allow concurrency
and ensure serializability.
– A protocol will generally not examine the precedence graph as it is
being created; instead, it will impose a discipline on the order in which
data items are accessed, which all transactions must follow, that avoids
nonseralizable schedules (i.e., it will restrict the allowable schedules).

☞ Concurrency control protocols trade-off between the amount of

concurrency allowed and the amount of overhead that is incurred to
ensure that schedules are serializable and recoverable.
