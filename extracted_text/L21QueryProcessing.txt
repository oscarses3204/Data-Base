SIZE ESTIMATION
The result size of an operation determines
i) the cost of the operation and
ii) the cost of subsequent operations.

☞ Its accurate estimation is important for query processing cost
estimation and for query optimization.

l

l

To estimate the result size of an operation, the database catalog keeps
various statistics about the sizes of data in the database.
These statistics should be updated whenever the database is updated.

☞ This can incur substantial overhead.
l

Consequently, DBMSs update their statistics only periodically.
☞ They are unlikely to be completely accurate but nevertheless are

sufficient for reasonable size (and cost) estimation in most cases.

SC(q, r) The selection cardinality, SC, of predicate q for relation r, is
the average number of tuples that satisfy the predicate q.
Selectivity(q, r) = SC(q, r) / nr (i.e., the fraction of tuples that satisfy q)

☞ Selectivity is a number between 0 and 1.
☞ The smaller the selectivity, the fewer tuples are selected
and the smaller the result size of an operation.

Projection: pA(r)

– The estimated size is V(A, r) (i.e., one tuple for each distinct A value).

– For union / intersection of selections on the same relation, rewrite

Ø Estimated size of r È s = size of r + size of s.

Ø Estimated size of r – s = r.

☞ All three estimates may be quite inaccurate,

QUERY OPTIMIZATION: OVERVIEW (cont’d)
Cost-Based Optimization
1. Generate logically equivalent evaluation plans using equivalence rules
for relational algebra expressions.
2. Estimate the cost of each plan.
3. Execute the plan with the minimum expected cost.
l

Estimation of the plan cost is based on:
– Statistical information from the database.

Ø The number of tuples, number of distinct values for an attribute, etc.

– Statistics estimation for intermediate results.

Ø To compute the cost of complex expressions.

– Cost formulae for algorithms, which are computed using statistics.

16.4.3

QUERY OPTIMIZATION: OVERVIEW (cont’d)
Heuristic Optimization
1. Perform first operations that reduce subsequent costs ⟹ perform
selections early.
Ø Reduces the number of tuples.

2. Remove unneeded attributes ⟹ perform projections early.
Ø Reduces the number of attributes (i.e., the size of each tuple).

3. Try to utilize existing indexes.

– Perform most restrictive selection and join operations before other similar
operations.

l

The goal is to transform the relational algebra tree by using a
set of rules that typically (but not in all cases) improves
execution performance.

☞ Some DBMSs use only heuristics while others combine
heuristics with partial cost-based optimization.

TRANSFORMATION OF RELATIONAL
EXPRESSIONS
l

16.2

Two relational algebra expressions are equivalent if they
generate the same set of tuples on every legal database instance.
– The order of the tuples generated is irrelevant.

– We do not care if they generate different results on databases that
violate integrity constraints.
l

SQL inputs and outputs are multisets of tuples (i.e., contain
duplicates).

– Two expressions in the multiset version of the relational algebra are
equivalent if they generate the same multiset of tuples on every legal
database instance.

l

An equivalence rule states that two forms of an expression are
equivalent.

☞ Can replace an expression of the first form
by one of the second, or vice versa.

EQUIVALENCE RULES: SINGLE OPERATIONS
Cascading of projections: pa1(R) ≡ pa1(pa2…(pan(R))…) where a1Ía2 … Ían
Example: psName(Sailor) ≡ psName(psName, sailorId(Sailor))

Ø Allows early removal of unwanted attributes to reduce intermediate result size.

Cascading of selections: sc1Ùc2…Ùcn(R) ≡ sc1(sc2…(scn(R))…)
Example: sage=20Ùrating>7(Sailor) ≡ srating>7(sage=20(Sailor))

Commutativity of selections: sc1(sc2(R)) ≡ sc2(sc1(R))
Example: srating>7(sage=20(Sailor)) ≡ sage=20(srating>7(Sailor))

Ø Allows early removal of unwanted tuples to reduce intermediate result size.

Commutativity of joins / Cartesian products: R ⨝ S ≡ S ⨝ R

Associativity of joins / Cartesian products: (R ⨝ S) ⨝ T = R ⨝ (S ⨝ T)
Ø Allows joins to be reordered to reduce intermediate result size.

QUERY PROCESSING: SUMMARY
Operation Processing

Selection: linear search; binary search; index lookup.

Sorting: external sort-merge if too large to fit into the buffer

Projection: sorting

Join: block nested-loop; indexed nested-loop; merge join; hash join

Expression evaluation: materialization; pipelining.

Query Processing
1. Transform an SQL query into a relational algebra expression.
2. Generate different query execution plans and evaluates their cost
based on the cost and result size of each operation using statistics
about the database.
3. Select an optimal query execution plan using heuristics and/or cost
estimates.
