Variable-length character string with maximum length n.1

4.4

INTEGRITY CONSTRAINTS (IC)
An integrity constraint (IC) ensures that authorized changes
to the database do not result in a loss of data consistency.

☞ An IC guards against accidental damage to the database.
l

l

ICs are obtained from the requirements of the real-world
application that is being described in the database relations.
–

An integrity constraint is a statement about all possible instances!

–

We know from common knowledge that an attribute like hkid is a key,
but in general the constraint that an attribute, such as accountNo, is a
key must be given to us by the client.

We can check a database instance to see if an IC is violated,
but we can never infer an IC by looking at a database instance.

RULES FOR UPDATABLE VIEWS
l

A view is updateable (i.e., tuples can be inserted, updated and
deleted) if all the following conditions are satisfied by the query
that defines the view.
– The from clause has only one relation.
– The select clause contains only attribute names of the relation, and
does not have any expressions, aggregates, or distinct specification.
– Any attribute not listed in the select clause can be set to null (i.e., it
does not have a not null constraint and is not part of a primary key.
– The query does not have a group by or having clause.

☞ The rules for view update are often
DBMS dependent.

ASSERTIONS

An assertion is an arbitrary SQL predicate that the database
must always satisfy.
An assertion takes the form:
create assertion <assertion-name> check <predicate>

l

Difference from previous constraints:
– A constraint is associated with a single relation and checked when
there is an update on this specific relation.
– An assertion may be associated with several relations and is
checked every time there is an update anywhere.

☞ Assertion testing may introduce a significant amount of
overhead and so should be used with great care.

ORACLE DATABSE: TRIGGER SYNTAX (simplified)
create [or replace] trigger trigger-name
{before | after} {delete | insert | update [of column-name ...]} or ... on table-name
[referencing {old as old | new as new} ...]
[ ] optional
[for each row]
{ } select one
... can repeat immediately
[when (condition)]
preceding construct
PL/SQL_block
l

l

l
l

l

l

before | after - specifies that the trigger should fire (execute) before/after executing the
triggering event (i.e., before or after a delete, insert or update statement).

delete | insert | update of column-name - specifies the statement that causes the trigger to fire;
more than one of the listed statements can be specified (e.g., before insert or after delete …).
on table-name - specifies the relation on which to create the trigger.

referencing {old as old | new as new} - specifies correlation names for old and new values of
the current row. The default correlation names are old and new. (e.g., old.balance refers to
the balance value before an update while new.balance refers to the balance value after an
update). When using old and new in a PL/SQL_block they must be preceded by a colon
(e.g., :old.balance).
for each row - specifies that the trigger fires once for each row that is affected by the
triggering statement and that meets the optional trigger constraint defined in the when
clause. If this clause is omitted, then the trigger fires only once and not for each row.
when (condition) - specifies the condition that must be satisfied for the trigger to fire.
