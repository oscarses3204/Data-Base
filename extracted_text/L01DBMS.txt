Data security problems

– Data may be duplicated in several files possibly leading to data inconsistency.
– Data are structured to meet the needs of specific applications; unanticipated data needs
often require writing new application programs to extract the required data.
– Related data are often scattered in different files and in different formats making writing
new application programs requiring related data challenging.
– Constraints on data become part of the program code making them hard to change and
making it hard to know what constraints apply.
– New constraints are often hard to enforce especially if they apply across several files.
– Since changes to data may involve several updates (e.g., a transfer of funds between
bank accounts), hardware/software failures can cause data to become inconsistent.
– Data may become lost or inconsistent due to simultaneous access by many users (e.g.,
lost update).
– Enforcing security of data can be challenging due to ad hoc data management.

1.3.1

DATA MODELS
A data model is the language used by a DBMS to describe how data
is organized and accessed.
It defines how users view and interact with the data in a database.
A data model usually consist of:
1. data structure types ⟹ specify logical data organization
(properties, relationships and semantics)

2. integrity constraints ⟹ specify restrictions on properties of the
data and the relationships among the data

3. operations

⟹ specify how data is accessed (e.g.,
R,I,U,D—Read, Insert, Update, Delete)

A data model is used to describe and organize data
as well as to possibly state restrictions on the data.

APPLICATION/DATA DEPENDENCE
l

l

A big problem in application development is often the
dependence of applications (i.e., the code) on the data that they
access.
Do I have to change my application when I …

– replace my disk (i.e., move the data to a new disk)?

– partition the data into two physical files (or merge two physical files
into one)?
– store salary as a floating-point number instead of an integer?
– develop other applications that use the same data?
– add more data fields to support other applications?

– index the data using a B+-tree instead of a hash index?

A DBMS can provide some degree of
application/data independence using
levels of data abstraction.

DATA INDEPENDENCE AND DATABASE SYSTEMS
l

Relational DBMSs provide data independence via schemas
following the three levels of data abstraction approach.
– The data semantics are represented in the schema (the description)
and are stored separately from the data (the facts) in the system
catalog.
– All data in the database must conform to the schema.
– Application programs and queries are usually simpler to develop.

l

Non-relational (NoSQL) DBMSs generally do not use schemas
(i.e., they are schemaless).
– The data semantics are either encoded in the applications (i.e., the
code) that access the database or are embedded within the data.
– The lack of a schema allows for flexibility in what data is stored.
– Application programs and queries are usually more complex to
develop.

GENERAL DBMS ARCHITECTURE:
STORAGE MANAGER
l

1.6.1

The storage manager provides the interface between the raw
data stored in the database (i.e., on physical storage devices)
and the application programs/queries that access the database.

☞ It is responsible for storing, retrieving
and updating data in the database.

l

The storage manager components usually include:
– buffer manager (fetches data from secondary storage and caches it
in main memory)
– file manager (manages allocation of secondary storage)
– authorization and integrity manager (controls database access;
enforces constraints)
– transaction manager (ensures database consistency despite system
failures and concurrent access by multiple users)

GENERAL DBMS ARCHITECTURE:
QUERY PROCESSOR
l

1.4, 1.6.2

The query processor translates application requests (i.e.,
queries and updates) into efficient device-level operations.

☞ It facilitates data access while providing good performance.
l

The query processor component includes either one or two
query languages:
– data definition language (DDL) defines the database schema
according to a data model. (Not relevant for most NoSQL DBMSs.)

– data manipulation language (DML) accesses and manipulates data.

Ø Procedural DML: the user specifies both what data is required and how to
get the data.
o Many non-relational DBMSs provide only a basic DML (e.g., get/put data).

Ø Nonprocedural (declarative) DML: the user specifies only what data is
required not how to get the data

o All relational DBMSs provide Structured Query Language (SQL), a nonprocedural
DML.
o Some non-relational DBMSs provide a DML similar to SQL.

DATABASE MANAGEMENT SYSTEMS: SUMMARY
l

l

l

l

Database management systems (DBMSs) address the
limitations of OS file systems for managing an organization's
data.
Data models are the foundation for developing a database—the
entity-relationship (E-R) model and relational model are
commonly used in practice for structured data while key-value
and document models are used for less structured data.
Data independence is fundamental to understanding how
relational DBMSs manages data at different data abstraction
levels. It is not a major concern for applications that use nonrelational (NoSQL) DBMSs.
A DBMS provides many facilities for data management and
data access to efficiently handle the data needs of a variety of
users and applications.
